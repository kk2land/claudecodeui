## cloudcli-workers 使用说明

本节约束 `cloudcli-workers` 的使用；下文“主代理”同时指 Codex 和 DSH。

- 小而明确的请求直接处理：问答、代码查找、文案或配置修改、局部修复，以及修改 skill 本身，都不因提及 `cloudcli-workers` 而委派。文件数或行数不是委派门槛。
- 用户意图优先：用户要求直接处理或仅委派部分工作时遵从。以整个用户任务判断是否采用 `cloudcli-workers`，适用于明确的 Worker 执行请求、已有任务管理，或目标、范围、验收明确且整体收益超过协调成本的较大任务。
- 一旦采用 Worker 执行，本次任务的调研、实现、测试和修复等执行性子任务全部交给 Worker。主代理负责需求、设计、计划、调度、review、集成与最终验收，不自行接管未派发的子任务或少量修复；用户明确指定部分委派时按指定范围执行。
- 决定委派前，技能被禁用、未启用，或当前会话的 Worker MCP 未连接、缺少所需工具时，跳过该 skill，直接用普通工具完成原任务，不要求先配置 MCP。已进入 Worker 流程后的持续调用失败如实报告，不自行接管执行子任务；任何情况下都不绕过 MCP 调用底层执行器或复制 runner。
- 接受前核对实际 diff 和验证证据，集成后完成必要的最终验收；需要修改代码时续接原 Worker 或派发后续 Worker，包括集成和验收发现的小修复。
- 派发时按本轮交付设置合理的 `timeoutSeconds`，长工作按可验收阶段续接；确需不限时须在交接中说明原因和停止条件。提示词须给出命令预算：长命令后台执行，单次同步等待不超过 60 秒；测试已报超时而进程未退出时，停止本任务自己的进程并保留日志。
- 首次预算提醒默认在 600 秒或 20 步触发；此前提醒已投递时，后续每 600 秒再次提醒，未投递的提醒不叠加。主代理每次核对当前 run，并对比上次的交付物、diff 和检查结果；只有新的有效产出才算进展，不能只凭 `running`、步骤增长或进程存活继续等待。有进展时等待下一次自动提醒，不自行轮询。
- 方向偏离、持续无进展或重复无效工作时，在原授权范围内取消该 Worker（`pause: false`），确认停止后用明确反馈续接同一 Worker；同一失败已在未修改基线上复现后，记录限制并继续剩余交付，不再重复完整测试。软提醒本身不触发自动取消，用户 Stop 后仍须等待用户明确继续。

### 计划阶段

符合委派条件时，在方案定稿前明确：

- 先按可独立实现和验收的交付物识别实现线。各线工作量足够、读写范围可隔离且共享契约可明确时，优先拆给不同 Worker 并行（如不同 provider 或组件），不默认由单个 Worker 承担全部实现；强耦合或拆分协调成本更高时保留单 Worker，不设机械的 Worker 数量或文件数门槛。
- 覆盖全部执行交付物的 W1/W2 等 Worker 分工，以及主代理的协调、review、集成与最终验收职责。
- 各自的工作区与读写范围。
- 共享接口指定唯一负责人，先明确并落地最小契约再放行依赖，避免少量共享接口把其余独立实现串行化。
- 依赖及启动条件；串行步骤和收尾工作也要指定 Worker。依赖产物必须真正进入下游 cwd 或 `baseRef`，独立 worktree 不会自动同步。
- 基线，以及局部验证项和需要返回的证据。
- 可并行项。MCP 排队没有 `dependsOn`，并发排队不能表达依赖。

派发新建任务时由主代理按任务的主要交付物标注单一 `taskRole`（测试、开发、UI设计、方案调研、方案审核、代码审核），
不根据提示词关键词猜测；`worker_resume` 沿用原类型，不传 `taskRole`。`ui_design` 仅限界面布局、视觉样式与交互，技术方案、架构设计和任务拆分由主代理
完成；`plan_research` 负责现状调研、可选方案对比并提供事实依据与建议，最终方案由主代理确定；`plan_review`
只审核主代理已有方案，决策与修订仍由主代理负责。`configId`、`type`/`model`/`provider`/`effort`
仍只在用户明确选择时传入；省略时由插件按已启用配置路由：可选的 `type` 先过滤引擎，再由 `taskRole` 取列表中第一个匹配配置
（默认配置不覆盖前面的匹配项），无匹配或未传角色时优先 `defaultConfigId`（若在候选中），否则取列表首项。设置页可拖动调整配置顺序，
该顺序就是路由顺序。`type` 只是配置的引擎过滤条件，不能替代配置；引擎（`dsh`/`pi`/`codex`）决定执行方式，
配置是对应引擎下具名的模型/角色/并发设置。`worker_context` 可读取 `settings.configs`、`settings.defaultConfigId`
及兼容投影 `settings.enabled`/`settings.roles`/`settings.concurrency`；旧调用缺少 `taskRole` 时仍按默认配置兼容。

允许在当前父会话与项目的 Markdown 计划中记录任务、依赖、验收进度和 worker/run 标识。主会话通过
`worker_context` 读取，通过 `worker_plan_save` 保存完整记录；保存不会启动任务或自动验收。
派发前由主会话确认前置任务已验收，且产物已进入下游工作区。计划调整、派发、验收、阻塞或返工时更新记录。
方案定稿不等于派发：计划模式下只形成方案；保存和派发均遵守当前会话模式与授权，仅启动已就绪任务。

### 计划阶段方案审核

- 方案审核只用于计划阶段形成的整体方案，不是每次改动的实施前置。进入实施后，修复、需求调整、契约调整和集成问题由主代理协调开发、测试与代码审核，不启动或续接 `plan_review` 做例行补审；只有明确重新进入计划阶段、制定新的整体方案时，才再次安排方案审核。用户明确指定的执行方式优先。
- 在计划阶段记录“方案规模：小/中/大、方案审核：需要/免审”及一句依据；中、大整体方案在定稿前完成审核。局部、沿用既有架构与接口且实现和验收明确的小方案可免审，不按文件数、行数、耗时或 Worker 数量单独判断。
- 计划中的完整功能、多模块联动为中方案；架构或核心流程调整、共享协议兼容、数据迁移、多线关键依赖及影响整体实现的未决技术取舍为大方案。缺少事实时先只读调研，由主代理形成可审核方案。
- 在计划阶段按当前会话模式与授权派发 `taskRole: "plan_review"`、`writePaths: []` 的 Worker，提供整体方案、基线、约束和验收条件，审核可行性、遗漏、兼容性与依赖。交付须明确审核结论；发现不合理之处时，说明问题与原因，并提出具体、可执行的调整建议；未发现问题时也须明确说明。
- 主代理在计划定稿时处理审核意见并记录结论，进入实施后复用已有结论。审核工具不可用时如实记录，按前述分流规则处理，不把审核自动推迟为实施阶段的新门槛。
- `plan_review` 检查准备采用的方案；`code_review` 检查已经完成的代码与测试。实施中发现缺陷时直接修复和验证，不退回方案审核。

### 合并后清理

- 主代理 review 并完成必要验证后，才在授权范围内合并；使用插件创建的 worktree 时，合并完成后必须对相应 Worker 执行 `worker_cleanup`。
- 仅当 worktree 由插件创建、工作区干净、Worker 已停止且无其他任务占用时清理。保留分支、原生会话和日志。
- 清理后该 Worker 不可续接；后续任务用 `worker_start` 新建 Worker，不再 `resume`。
