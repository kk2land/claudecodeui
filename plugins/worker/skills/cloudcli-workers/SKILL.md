# CloudCLI Worker 协调

主代理负责需求、设计、计划、调度、review、集成与验收；采用 Worker 后，调研、实现、测试、修复全部委派，包括返工和集成小修，用户明确部分委派除外。Worker 不得递归派发、commit、merge、push 或清理 worktree。

## 分流与计划

- 按整个任务判断：明确要求 Worker、管理已有任务，或目标/范围/验收明确且委派收益超过协调成本时使用。小请求、局部修改及修改本技能直接处理；用户指定方式优先，不按文件数或行数设门槛。
- 委派前技能禁用、MCP 或所需工具不可用时直接处理；工具与环境须在 Worker 可用。进入流程后调用持续失败须报告，不自行接管，也不绕过 MCP 调用执行器。
- 决定委派后调用一次 `worker_context`，确认父会话、项目、并发、状态、`settings.enabled`/`roles` 和 `plan`；同轮复用，范围变化或恢复上下文时刷新，并核对计划与实际状态。
- 按独立交付物拆线：工作量足、读写隔离且契约明确时优先并行；强耦合或协调成本更高时用单 Worker。共享契约指定唯一负责人；分工覆盖共享接口、串行步骤和收尾。
- 每个父会话与项目维护完整 Markdown 计划：目标、方案规模及审核依据、任务/依赖、cwd/基线/读写范围、验收条件、worker/run 标识、进度/证据和产物位置。新目标追加，完成项保留简短结论。
- 用 `worker_plan_save({ content })` 替换完整计划，仅在调整、派发、验收、阻塞或返工时保存。保存不触发执行或验收；计划模式只形成方案，保存和派发均遵守当前模式与授权。
- 依赖须经主代理验收，且产物已进入下游 cwd 或 `baseRef` 才能放行，记录交接依据。独立 worktree 不自动同步，MCP 排队没有 `dependsOn`。

## 实施前方案审核

首次派发实现前，在计划记录“小/中/大、需要/免审及依据”；未进入计划模式也适用，用户明确指定方式优先。

- **小方案可免审**：局部修改，沿用架构和接口，实现与验收明确，且不涉及下述事项。
- **中方案必审**：完整功能或流程需跨模块协作、多个关联步骤或行为联动与集成验收，超出局部修改；接口不变、路径明确或单 Worker 均不构成免审理由。
- **大方案必审**：架构/核心流程调整、共享接口/协议兼容性变化、数据迁移、多线关键依赖或影响整体实现的未决技术取舍。不按文件数、行数、耗时或 Worker 数量单独判断；缺少事实则先只读调研，由主代理形成方案。
- 计划模式只安排审核及依赖；获准实施后先派 `taskRole: "plan_review"`、`writePaths: []` 的 Worker，提供完整方案、基线、约束和验收条件，审核可行性、遗漏、兼容性与依赖。主代理记录意见处理和修订，解决阻塞并验收后才派实现。
- 已有审核覆盖当前方案则复用；架构、契约或关键依赖实质变化时仅补审受影响部分。审核失败或不可用记为阻塞，不静默免审；委派前技能/MCP 不可用仍按分流规则处理，并说明未完成独立审核。

## 派发与续接

- 使用已确认的上下文，不猜身份；先保存计划再派发，接受后回填 worker/run 标识。交接须自包含目标、背景、约束、依赖、验收、中途交付与停止条件，明确 `writePaths`（相对 cwd；只读为 `[]`）。需要示例时读 [协作案例与模板](references/workflows.md)，已有事实直接提供。
- `worker_start` 显式选 `workspace.mode`：`existing` 的写入不重叠，`worktree` 隔离并可指定 `baseRef`。脏源默认拒绝；仅已授权、确认不依赖未提交改动且记录基线后用 `allowDirtySource: true`。
- 每次启动/续接用新 `requestId`，仅同一操作和载荷重试时复用；不重复派发同一目标。新建按主要交付物选单一 `taskRole`：`testing`/`development`/`ui_design`/`plan_review`/`code_review`，不按关键词猜。UI设计仅负责界面/视觉/交互，方案设计由主代理负责，方案审核仅审已有方案。
- `type`/`model`/`provider`/`effort` 仅传用户明确选择；省略 `type` 按已启用类型和角色匹配，无匹配则回退默认，显式类型须已启用。reasoning 对应 `effort`，合法组合以 MCP schema 和服务端为准。
- `worker_resume` 用原 workerId、cwd、home 和原生会话，不传 `taskRole`；模型/effort 沿用原 run，除非用户指定覆盖。只读任务不得续接为写入任务。
- 按本轮交付设置 `timeoutSeconds`，长任务分阶段续接；`null` 须说明原因与停止条件。提示词给出命令预算：长命令后台执行，同步等待不超过 60 秒；测试超时但进程未退出时停止本任务进程并保留日志。

## 运行、验收与纠偏

- start/resume 接受即返回，可能排队；继续处理已就绪任务或独立工作，仅剩等待时简报状态并交还回合。新任务不自动 steer/取消原 Worker。
- 收到通知或需查询时用 `worker_list`/`worker_get`，复用响应；按 `notifications[].id` 批量 `worker_ack`，重试复用 ID。`completed` 和 ack 均不代表验收。`worker_wait` 仅限用户要求等待或必要短查，单次最多 25 秒，不循环轮询保活。
- 验收核对实际 diff 与验证证据，集成后完成必要最终验收；不足时按 run/stream/cursor 增量读 `worker_logs`，日志不改变执行边界。结论、证据和交接写回计划，未验证项明确标注；报告改动、验证、阻塞和 worker/run 标识，旧计划不证明 Worker 可续接。
- 仅因新改动、失败或未决问题重跑；同一失败已在未修改基线复现则记录限制，继续剩余交付，不重复完整测试。
- 首次预算提醒默认 600 秒或 20 步，已投递后每 600 秒再提醒，未投递不叠加。提醒时先 `worker_get` 核对当前 run，比较实际产物、diff 和验证；running、步数和进程存活不算进展。有新产出则等下次自动提醒，软提醒不自动取消。
- 偏离或持续无进展时，对原 workerId 用 `worker_cancel(pause: false)`，确认停止后 resume，说明偏差、保留结果、下一交付及检查/停止条件。反复无进展或 MCP 持续失败时报告事实、原始错误与已尝试调用，停止派发；无新证据不重试。用户或宿主 Stop 后须等明确继续。
- 普通问题在 Worker 范围内解决；改变范围、契约、验收或缺少依赖时返回事实和缺口，由主代理决定并更新计划。返工优先续接原 Worker。
- unknown/取消未确认不得续接；核实原生会话和进程已停止后，才用 `worker_recover(notes, confirmedStopped: true)` 恢复，不重跑。

## 合并与清理

主代理 review 和验证后按授权合并；插件创建的 worktree 合并后必须 `worker_cleanup`，须干净、已停止且无人占用。保留分支、原生会话和日志；清理后不可 resume，后续用 start 新建。
