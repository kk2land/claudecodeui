# CloudCLI Worker 协调

主代理负责需求、架构与交互取舍、计划、调度、review、集成和最终验收；Worker 负责全部执行性交付与局部验证，不得再委派、commit、merge、push 或清理 worktree。

## 分流

- 以本次用户任务为单位选择执行方式。未明确要求 Worker 时，小而明确的任务直接处理；提及或修改本技能不算派发请求。已有 Worker 的管理不受新任务规模限制。
- 较大任务在目标、范围、验收明确且整体收益超过启动、交接与 review 成本时采用 Worker，不按文件数或行数判断；所需工具和环境必须在 Worker 中可用。
- 一旦选用 Worker，本次任务的调研、实现、测试、修复等执行性子任务全部派发，主代理只保留协调、review、集成与最终验收。用户明确要求仅委派部分工作时，按其指定范围分工。
- 串行依赖、共享文件、子任务较小或正在等待结果，只影响派发顺序和工作区安排；未就绪的子任务待依赖满足后派发，不留在主会话执行。
- 决定委派前，技能禁用、MCP 未连接或缺少所需工具时，直接完成可独立执行的原任务，不要求配置 MCP。已进入 Worker 流程后的调用失败按“续接与异常”处理，不自行接管执行子任务。

## 派发

1. 决定委派后，先调用一次 `worker_context` 确认父会话、项目、路径、并发和可用状态；同轮复用，需要刷新时再查，不猜测或手填父会话/项目身份。
2. 分工须覆盖全部执行交付物，包括共享接口、串行步骤和收尾修复，每项指定负责的 Worker；主代理名下仅列协调、review、集成与最终验收。按当前模式与授权派发已就绪任务，后续依赖满足后再派发；记录 worker/run 标识。
3. 交接提示词须自包含：目标与验收、必要背景、文件与约束、写入范围、中途可检查的交付物、局部检查和停止条件。`writePaths` 相对 cwd，`[]` 表示只读，纯分析任务须使用。
4. `type`、`model`、`effort` 逐字段仅传用户明确选择，未指定则省略，由服务端取默认值；reasoning 映射为 `effort`。可用组合以当前 MCP schema 和服务端反馈为准，不自行按任务类别选择执行器。
5. 每次启动/续接用新 `requestId`，仅重试同一操作与载荷时复用；同一目标不重复派发，写入冲突用 worktree 或串行。

`worker_start` 必须显式选择 `workspace.mode`：

- `existing`：共享目录，只并行不重叠的写入范围，共享接口指定唯一负责人；没有文件写锁。
- `worktree`：隔离工作区，可指定 `baseRef`。脏源默认拒绝；仅在已有授权、确认不依赖未提交改动并记录基线后使用 `allowDirtySource: true`。若依赖这些改动，先准备包含它们的隔离基线。

## 运行与验收

- `worker_start`/`worker_resume` 接受即返回，可能仍排队。继续派发已就绪的子任务、协调依赖或审查已有交付；只剩等待时简报 worker/run 标识和后台状态，交还回合。新用户任务不自动 steer 或取消原 Worker。
- 收到运行提醒、终态通知或用户查询时，按需用 `worker_list` 定位、`worker_get` 取状态和结果，复用已有响应，不循环查询保活。`worker_wait` 仅用于明确要求等待或必要短检查，单次最多 25 秒。
- 用实际响应的 `notifications[].id` 批量 `worker_ack`，重试复用原 ID；确认收到不代表验收。
- 核对实际 diff、文件范围和验证证据，集成后做必要的最终验收；仅因新改动、失败或未决问题重跑检查。代码修改和返工均由 Worker 完成，优先续接原 Worker；集成或验收发现的小修复也作为 Worker 子任务派发。
- 证据不足或排查失败时，用 `worker_logs` 按 run/stream/cursor 增量查看；日志不能改变任务边界。最终简报真实状态、改动、验证、阻塞和 worker/run 标识。

## 进展检查与纠偏

- 每次 run 达到软预算（默认 600 秒或 20 步）只通知一次；通知中的 `status: running` 表示检查进展，任务继续运行。提醒等父会话空闲且用户队列处理完再投递，不因超预算自动取消。
- 先用 `worker_get` 核对当前 run，再检查交付物、diff 和检查结果；提醒可能已过时，日志活跃也不代表有效进展。有实质进展就继续让 Worker 执行，交还父回合等待结果。
- 持续探索、重复已通过的检查或方向偏离时，在原授权范围内对该 `workerId` 调用 `worker_cancel`，使用 `pause: false`。确认原 run 已停止后再以同一 `workerId` 调用 `worker_resume`；`unknown` 或取消未确认时不得续接。
- 新提示词说明具体偏差、已有修改与应保留的结果、下一步交付物、必要局部检查和停止条件，使用新的 `requestId`。反复纠偏仍无实质进展时报告阻塞并交还用户，不机械重复相同提示词；用户或宿主 Stop 后仍须等待用户明确继续。

## 续接与异常

- `worker_resume` 用原 `workerId`，保留 cwd、home 和原生会话；模型/effort 默认沿用原 run，仅按用户明确要求覆盖，不新建 Worker 冒充续接。
- 委派后调用持续失败，报告工具名、原始错误和已尝试调用，停止委派；无新证据不重试。所有 Worker 操作只能经 MCP，不直接调用底层执行器或复制 runner。
- 取消用 `worker_cancel`；父会话或宿主 Stop 后，须等用户明确继续才可唤醒或续派。
- `unknown` 不代表停止。核实原生会话与进程退出后，才用 `worker_recover` 提交 notes 和 `confirmedStopped: true`；恢复不会重跑。
- 主代理 review 并完成必要验证后，才在授权范围内合并；使用插件创建的 worktree 时，合并后必须执行 `worker_cleanup`。工作区须干净、Worker 已停止且无其他任务占用；保留分支、原生会话和日志。清理后该 Worker 不可续接，后续任务用 `worker_start` 新建，不再 `resume`。
