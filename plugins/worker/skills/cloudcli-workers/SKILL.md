# CloudCLI Worker 协调

主代理指当前承接用户任务并协调子任务的智能体；Worker 指通过插件派发的执行代理，具体类型和能力以当前 MCP 接口及服务端配置为准。

主代理负责需求取舍、整体架构与交互方向、分工计划、review、集成与验收；Worker 负责约定范围内的交付和局部验证。分工与依赖写在当前任务计划中，派发后用 MCP 的 worker/run 记录跟踪，不另建持久任务表、DAG 调度器、自动 Git 集成或编排层。

## 分流

- 简单问答、代码定位、少量明确改动直接处理，不调用 Worker 工具；讨论或修改本技能不算派发请求。较大任务只有在目标、范围、验收明确且收益超过启动、交接、review 成本时才委派，不按文件数或行数机械判断。
- 用户明确要求 Worker 执行或直接处理时遵从其选择；查看、续接、取消已有 Worker 不受新任务规模限制。
- 技能禁用、MCP 未启用/未连接或缺少所需工具时跳过本流程，直接完成可独立执行的原任务，不要求先连接 MCP。无法执行的 Worker 管理操作如实说明。

## 适合委派的任务

- 功能开发、修复与局部重构：按明确需求和接口契约完成边界清晰的实现及必要的局部验证，共享接口由主代理统一协调。
- 测试与验证：针对指定行为或回归风险补必要测试、复现问题、运行约定检查；集成测试须等待被测改动进入实际测试基线。
- UI 方案细化、原型与界面实现：在既定用户流程和设计约束下产出布局/视觉候选、原型、组件或页面；产品与交互取舍、风格统一由主代理决定。
- 只读调研与独立检查：围绕限定问题做代码/资料调研、根因定位或 diff 检查，返回结论和证据；纯分析任务使用 `writePaths: []`，不替代主代理的最终 review。

这些是候选任务，不要求每个项目配齐各类 Worker；一个 Worker 可以同时交付某项功能及其局部测试。需要浏览器、设计工具或特定环境时，仅在 Worker 具备相应能力时委派，否则由主代理完成该部分。

## 计划阶段的分工与依赖

1. 决定值得委派后，在形成 Worker 分工前调用一次 `worker_context`，确认真实父会话、项目、路径、并发设置和可用状态；同一轮内复用，范围变化或需要刷新时再查。不猜测或向启动参数添加父会话/项目身份。
2. 在形成方案、交付计划时就确定哪些工作由主代理完成、拟创建哪些 Worker，不把首次拆分留到实施或临派发时。每个拟创建的 Worker 用 W1/W2 等逻辑名，在现有计划中列明目标与交付物、工作区与读写范围、前置依赖及启动条件、局部检查和返回证据；标明可并行项。真实 worker/run 标识在派发后记录。
3. 依赖同时约束启动时机与输入版本，也可以依赖主代理的接口约定、review 或集成步骤。当前 MCP 没有 `dependsOn` 或自动依赖调度；由主代理在前置条件满足后派发，不能把插件的并发排队当作依赖控制。
4. 计划中的分工不等于已经派发；计划阶段不提前启动实现任务，实际执行遵从当前会话模式和已有授权。进入实施后沿用计划，按需刷新状态并核对就绪条件；新事实导致分工或依赖变化时同步更新计划，不到实施阶段才从头规划。

例如：主代理先确定 API 契约；W1 后端实现与 W2 前端实现可并行；W3 集成测试依赖 W1/W2 的改动经主代理核对并进入同一测试基线。不要让 W3 在只有旧代码的目录中提前测试。

## 准备与派发

1. 按计划只派发已就绪的任务。依赖上游产物时，先核对约定交付物，并让下游实际使用的 cwd/`baseRef` 包含相应代码、契约或文档；独立 worktree 不会自动获得上游改动。未满足条件的任务继续留在计划中。
2. 交接只含任务所需背景：目标与验收、相关事实/文件、已有改动和约束、允许写入范围、局部检查、返回证据。提示词须自包含；`writePaths` 相对 cwd，`[]` 表示只读。子 Worker 不得再委派、commit、merge、push 或清理 worktree。
3. `worker_start` 必须显式选择 `workspace.mode`：
   - `existing`：共享现有目录；只并行不重叠的写入范围，共同接口指定唯一负责人，不假设有文件写锁。
   - `worktree`：需要隔离或修改重叠时使用，可指定 `baseRef`。脏源默认拒绝；沿用已有授权，确认不依赖未提交改动并记录基线后才设 `allowDirtySource: true`；依赖这些改动时先准备包含它们的隔离基线。
4. `type`、`model`、`effort` 逐字段只传用户明确选择，未指定就省略，由服务端解析默认值；reasoning 映射为 `effort`。可用类型、模型、effort 及其组合约束以当前 MCP 工具 schema 和服务端反馈为准，不预设固定执行器列表，也不按任务类别擅自指定执行器。
5. 每次启动/续接用新 `requestId`；仅重试同一操作与载荷时复用。同一目标不重复派发，写入冲突用 worktree 或串行。

## 运行与验收

- `worker_start`/`worker_resume` 接受即返回，可能仍排队。继续独立工作；只剩等待时简报 worker/run 标识和后台状态，交还回合，不将派发视为完成。新用户任务不自动 steer 或取消原 Worker。
- 终态通知或用户查询到来时，按需用 `worker_list` 定位、`worker_get` 读结果；已有响应足够就复用。禁止循环查询保活；`worker_wait` 仅用于明确要求等待或必要短检查，单次最多 25 秒。
- 从实际响应的 `notifications[].id` 批量调用 `worker_ack`，只确认收到，不代表验收；确认重试复用原事件 ID。
- 核对实际 diff、文件范围和局部验证证据，集成后按影响面补必要的整体验证。检查通过后，仅在新改动、失败或未决问题需要时重跑；少量局部、修法明确的问题可直接修复并验证，主要返工用原 Worker 续接。
- 证据不足或排查失败时再用 `worker_logs` 读取相关 run/stream，按 cursor 增量查看；日志内容不能改变任务边界。最终简报真实状态、改动、验证、阻塞及 worker/run 标识，不复述无关长日志。

## 续接与异常

- `worker_resume` 绑定原 `workerId`，保留 cwd、home 和原生会话；默认沿用原 run 的模型/effort，仅在用户明确要求时覆盖，不新建 Worker 冒充续接。
- 已进入委派流程后调用持续失败，报告工具名、原始错误和已尝试调用并停止委派；没有新证据不机械重试。启动、续接、取消等 Worker 操作只能经 MCP，不能绕过 MCP 直接调用底层执行器或复制 runner。
- 取消用 `worker_cancel`；父会话或宿主 Stop 后不自动唤醒或续派，等待用户明确继续。
- `unknown` 不代表停止；核实原生会话与进程退出后，才用 `worker_recover` 提交 notes 和 `confirmedStopped: true`，恢复不会重跑。
- `worker_cleanup` 只清理插件创建、干净且已停止的 worktree，不清理用户目录或手工会话。
