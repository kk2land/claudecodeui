# 角色与配置路由

按需读取。判规模、判角色含义或需要覆盖预算时使用，常规派发不必读。合法组合与具体默认值以 MCP schema、服务端和设置页为准。

## taskRole

新建任务按主要交付物标注单一 `taskRole`，不按提示词关键词推测。`worker_resume` 沿用原类型。

| 角色 | 职责 |
| --- | --- |
| `development` | 实现改动并自测 |
| `testing` | 编写并运行验证，覆盖验收条件 |
| `ui_design` | 界面布局、视觉样式与交互 |
| `code_review` | 审查已完成代码与测试，指出缺陷与风险 |
| `plan_research` | 现状调研与可选方案对比，提供事实依据与建议 |
| `plan_review` | 只读审核主代理已有的整体方案 |

技术方案、架构设计和任务拆分由主代理完成。`plan_review` 审已有方案、写入范围为 `[]`，决策与修订仍由主代理负责。写入范围按任务裁剪，不按角色默认绑定。只读任务不能续接为写入任务。

## 方案规模

- 小：局部改动，沿用既有架构与接口，实现和验收明确，可免审。
- 中：计划中的完整功能、多模块联动。
- 大：架构或核心流程调整、共享协议兼容、数据迁移、多线关键依赖、影响整体实现的未决技术取舍。
- 中、大整体方案在定稿前完成 `plan_review`。不按文件数、行数、耗时或 Worker 数量单独判断。缺少事实时先只读调研，再由主代理形成可审核方案。

## 配置排序

- `configId`、`type`、`model`、`provider`、`effort` 只在用户明确选择时传。
- 省略时按已启用配置路由。`configId` 最优先，须存在且启用。否则可选的 `type` 先过滤引擎，再由 `taskRole` 取列表中第一个匹配配置，默认配置不覆盖前面的匹配项。无匹配或未传角色时优先 `defaultConfigId`（若在候选中），否则取列表首项。
- 设置页的配置拖动顺序就是该路由顺序。`type` 只是引擎过滤条件，不能替代配置。显式 `type` 须与 `configId` 一致。
- reasoning 对应 `effort`，合法组合以 MCP schema 和服务端为准。

## 例外预算

- 需要覆盖本轮预算时才显式传 `timeoutSeconds`，长任务按可验收阶段续接。
- 传 `null` 关闭本轮硬超时，须在交接中说明原因与停止条件。
